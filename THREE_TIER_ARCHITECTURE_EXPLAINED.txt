1. HIGH-LEVEL OVERVIEW: WHO IS IN EACH TIER?
--------------------------------------------------------------------------------

The platform is built as a multi-tenant SaaS hierarchy using a single shared
database logically partitioned by company_id and partner_id.

In business terms, there are THREE primary commercial tiers, plus the end
corporate employees (Learners) who take the training:

  +--------------------------------------------------------------------------+
  | TIER 0 (LEVEL 0): PLATFORM CREATOR / HRYAAR TECH MASTER                  |
  | Role: SUPER_ADMIN (alias: PLATFORM_ADMIN)                                |
  | Who:  The Tech Person at HRYAAR (you / platform owner)                   |
  | What: Owns the platform, provisions Middleman Partners and Direct        |
  |       Clients, manages plans, monitors cluster telemetry & audit logs.   |
  +--------------------------------------------------------------------------+
                     |                                  |
       Sells wholesale seat pools             Can also onboard
       to mutually exclusive Middlemen        Direct Clients directly
                     |                        (partner_id = NULL)
                     v                                  |
  +--------------------------------------+              |
  | TIER 1 (LEVEL 1): MIDDLEMEN /        |              |
  | ASSIGNER PARTNERS                    |              |
  | Role: PARTNER_ADMIN                  |              |
  | company_type = "PARTNER"             |              |
  |                                      |              |
  | Examples:                            |              |
  |  - Partner A: TalentPro HR Advisory  |              |
  |  - Partner B: Apex Compliance        |              |
  |                                      |              |
  | Rule: MUTUALLY EXCLUSIVE.            |              |
  | Partner A cannot see Partner B or    |              |
  | Partner B's clients (and vice versa).|              |
  +--------------------------------------+              |
            |                  |                        |
   Onboards & assigns     Onboards & assigns            |
   Client Acme & Nexus    Client Beta                   |
            v                  v                        v
  +--------------------------------------------------------------------------+
  | TIER 2 (LEVEL 2): CLIENT COMPANIES (END-USER ENTERPRISES / HR ANALYTICS) |
  | Role: COMPANY_ADMIN (alias: HR_ADMIN), HR_MANAGER, IC_MEMBER             |
  | company_type = "CLIENT"                                                  |
  | partner_id = <Partner's Company ID> (or NULL if Direct Client)           |
  |                                                                          |
  | Examples:                                                                |
  |  - Acme Cloud Systems     (partner_id = TalentPro)                       |
  |  - Nexus BioSciences      (partner_id = TalentPro)                       |
  |  - Beta Precision Mfg     (partner_id = Apex)                            |
  |                                                                          |
  | What: HR Professionals log in to view compliance analytics, webinars,    |
  |       department completion, employee audit roster, CSV import, & IC.    |
  +--------------------------------------------------------------------------+
                                     |
                      Enrolls / imports workforce
                      (via CSV or LMS webhook)
                                     v
  +--------------------------------------------------------------------------+
  | LEVEL 3 (WORKFORCE): CORPORATE EMPLOYEES / MANDATED LEARNERS             |
  | Role: EMPLOYEE                                                           |
  | What: Individual staff log in to complete 3 PoSH modules, pass the       |
  |       scenario quiz (>= 70%), download a Section 21 certificate,         |
  |       and access confidential IC grievance filing.                       |
  +--------------------------------------------------------------------------+

Note on Terminology in Code vs Business Intent:
In the UI and docs, you will sometimes see "Level 0, 1, 2, 3" (4 views) because
Employee Learners (EMPLOYEE) have their own dedicated Learner Portal separate
from their company's HR Analytics Dashboard (COMPANY_ADMIN).

    If a PARTNER_ADMIN requests a requested_company_id, the server checks:

          raise HTTPException(403, "Forbidden: Cross-partner data access prohibited")

3. HOW THE DATABASE STORES THE HIERARCHY
--------------------------------------------------------------------------------

All organizations (both Middlemen and Clients) are stored in the SAME table:
`companies`.

They are linked via a self-referential foreign key:
  Company.company_type  -> "PARTNER" or "CLIENT"
  Company.partner_id    -> Points to another Company.id (the Middleman's id)
                           or NULL if onboarded directly by Tier 0 Super Admin.
  Company.partner_name  -> Cached string name of the partner
  Company.assigned_seat_quota -> Seat capacity (pool for Partner, limit for Client)

And all users across all tiers are stored in the `users` table:
  User.role       -> "SUPER_ADMIN" | "PARTNER_ADMIN" | "COMPANY_ADMIN" |
                     "HR_MANAGER"  | "IC_MEMBER"     | "EMPLOYEE"
  User.company_id -> NULL for SUPER_ADMIN, or Company.id for everyone else.

4. HOW LOGOS & BRANDING WORK ACROSS TIERS
--------------------------------------------------------------------------------

- Every company has its own `logo_url` and 4 theme colors (`primary_color`,
  `secondary_color`, `accent_color`, `sidebar_color`).
- `frontend/src/components/brand/CompanyLogo.tsx` renders either the uploaded
  image (if valid) or a bespoke vector emblem per company slug (`hryaar`,
  `talentpro`, `apex`, `acme`, `beta`, `nexusbio`), or initials + primary_color
  for newly created companies.
- Because `get_tenant_company_id()` scopes every query to one company, Company A
  never receives Company B's logo_url, colors, or records.
- For Partner-managed clients, `co_branding_mode` controls whether the Partner's
  name/logo badge ("Managed by TalentPro") is shown alongside the Client's logo.

5. CURRENT QUIRKS / GAPS IN THE CODE TO KEEP IN MIND WHEN REFINING
--------------------------------------------------------------------------------

As you refine how the three tiers should work, note these exact behaviors in the
current codebase:

1. Creating a Partner via Tier 0 UI assigns the wrong user role:
   - In `backend/app/api/v1/super_admin.py` (create_company, line ~161), when
     Super Admin creates a company with `company_type="PARTNER"`, the initial
     user is hardcoded with `role="COMPANY_ADMIN"` instead of `"PARTNER_ADMIN"`.
     (Only seeded partners in `seed.py` currently have `role="PARTNER_ADMIN"`.)

2. Partner Seat Re-Allocation button is not wired on the backend:
   - In `frontend/src/components/partner/PartnerDashboard.tsx` (line 126), the
     "Allocate Seats" modal calls:
       `POST /api/v1/partner/clients/{id}/allocate-seats`
     However, `backend/app/api/v1/partner.py` does NOT currently have that
     route, so clicking Save Quota in that modal will return 404.
   - Also, `POST /api/v1/partner/clients` does not currently block a Partner
     from assigning more total seats than `partner.assigned_seat_quota`.

3. Middleman role scope ("simply assigners"):
   - Right now, Partners can:
     (a) Onboard clients and set initial seat quota,
     (b) View aggregated client completion %,
     (c) Click "Inspect Client" to open the full Client HR Dashboard,
     (d) Edit co-branding modes.
   - If you want Middlemen to be PURELY assigners (only provisioning clients and
     assigning seats/licenses, without inspecting employee rosters/complaints),
     the "Inspect Client" view and client analytics metrics can be restricted.

4. Client User role scope ("simply HR professionals for analytics"):
   - Right now, Client HR Admins see the 7 core analytics items on the main
     Dashboard Pulse tab, PLUS 10 additional operational tabs in the left sidebar
     (Complaints, IC Members, Compliance Docs, Webhooks, Branding, Settings, etc.).
   - If you want Client accounts streamlined purely for analytics + CSV/reminders,
     or kept split between HR Analytics vs IC Redressal Officer, that can be
     cleanly separated by role (`HR_MANAGER` vs `IC_MEMBER` vs `COMPANY_ADMIN`).

5. Employee Seat Quota Enforcement:
   - `Company.assigned_seat_quota` exists on both Partners and Clients. We should
     confirm whether adding/importing employees in a Client company must strictly
     block once `total_employees >= assigned_seat_quota`, and whether Partner's
     pool strictly deducts from `partner.assigned_seat_quota`.

6. Super Admin User Management Modal:
   - In `SuperAdminDashboard.tsx`, creating a user should clearly allow choosing
     `PARTNER_ADMIN` when linking a user to a `PARTNER` company.
